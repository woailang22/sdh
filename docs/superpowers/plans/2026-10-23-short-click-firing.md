# Preserve short ranged clicks between animation updates

**Goal:** A valid ready ranged click produces exactly one shot even if mouseup precedes the next update, preserving current cooldown, ammunition, targeting and held-fire behavior.

**Evidence:** Production063abe8 native three-Chrome diagnostic a20 at empty world ground: twelve40ms requests each fired once; of four5ms requests, one actual13.7ms click had no update between down/up, no client round spent, no fire packet and no server round spent. This confirms an input sampling gap, not a server rejection. The earlier a17 untraced40ms failure remains unexplained. a19 was a QA readiness mistake (forgot nativeR reload); preserve it separately.

**Approach:** Reuse one ranged-shot method from both mousedown and the existing held-fire update. On left mousedown refresh the aim from that event's canvas coordinates before attempting a shot. The same nextShotAt guard is updated before sending, so the next frame or another click cannot double fire or bypass cooldown. Original editor/build/input-blocked branches still take priority. Because the first attempt now happens outside the frame's error boundary, catch/report input shot failures through the existing bounded diagnostics and stop held input; never automatically retry or roll back possibly sent actions. Do not add a pending input queue, deferred released shots, new input rate, weapon changes, server acceptance exceptions or melee changes.

**Alternatives:** A next-update latch needs cancellation/expiry/aim and equipment context, and can fire after release or mode changes. Increasing the update rate does not guarantee a frame between down/up and adds CPU work. Immediate guarded ranged attempts use the present input/weapon/space and remove the sampling dependency directly.
